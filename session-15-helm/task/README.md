## Key ideas, in my own words

- **Chart:** a folder of templated Kubernetes YAML plus `Chart.yaml` (name, chart `version`, `appVersion`) and `values.yaml` (defaults).
- **Release:** one installed copy of a chart in a namespace, with a name. The same chart can be installed many times under different release names.
- **Revision:** every install, upgrade and rollback of a release gets a new number. A rollback does not go "back" to an old number; it creates a new revision whose content is copied from the old one.
- **Values precedence:** chart `values.yaml` < files passed with `-f` (later files win) < `--set` on the command line. I proved this with `helm template` in Task 2.
- **Rendering:** Helm runs the Go templates with `.Values`, `.Release`, `.Chart` and produces plain YAML. `helm template` does this locally with no cluster; `install` / `upgrade` render the same way and then send the YAML to the API server.
- **Where Helm keeps state:** Helm 3 has no server side component. Each revision is stored as a Secret named `sh.helm.release.v1.<release>.v<revision>` of type `helm.sh/release.v1` in the release's namespace. Inside is base64 + gzip JSON with the chart, the values and the rendered manifest. That is why `helm history` and `helm rollback` work, and why `helm uninstall` deletes them.

## Task 2 - Full rollback workflow (Install, Upgrade, Verify, Upgrade, Verify, Rollback, Verify)

For this I wrote a small chart, `webapp-chart/`. The home page is an `index.html` in a ConfigMap built from values (`page.version`, `page.message`, `image.tag` and `.Release.Revision`), so I can **see** which version is live with curl, not only in `helm history`. The Deployment has a `checksum/page` annotation (sha256 of the rendered ConfigMap), so a page change also rolls the pods.

### 3.4 Deliberately bad upgrade

I used `--wait --timeout 60s` so Helm waits for the pods and reports the failure. I also passed `-f values-prod.yaml` again: `helm upgrade` starts from the chart defaults every time, so with only `--set image.tag=...` (as in the course notes) the release would also drop to 1 replica and `development`.

What happened:

- Helm waited the full 60 s and failed with `context deadline exceeded`. Revision 3 is marked `failed`.
- Helm did **not** undo anything by itself. The new pod is stuck in `ImagePullBackOff` (`NotFound` from Docker Hub).
- The app stayed up: the 3 old `nginx:1.25` pods are still running and curl still gets 200. With 3 replicas the RollingUpdate defaults (25%) round down to `maxUnavailable=0` and up to `maxSurge=1`, so Kubernetes created only one new pod and removed no old pod.

## What I learned

- A rollback is a new revision built from an old revision's stored manifest and values. It does not re-render templates, so `.Release.Revision` inside the page stayed `2` while the release was at revision 4.
- Without `--wait`, Helm reports success as soon as the API server accepts the YAML. With `--wait` a bad image becomes a `failed` revision, but only `--atomic` undoes it automatically.
- `helm upgrade` does not remember earlier `-f`/`--set` values unless I pass them again (or use `--reuse-values`), so every upgrade command needs the full set of values.
- All Helm state lives in `helm.sh/release.v1` Secrets in the release namespace. Reading them with `base64 -d | base64 -d | gunzip` showed exactly what `helm get values` and `helm history` read.
- A rolling update with 3 replicas kept the old pods serving during the failed upgrade, so the bad release did not cause downtime. Helm and the Deployment controller protect against different failures.

## Problems I hit

- **`helm create` default image.** The default tag comes from `appVersion: 1.16.0` (an old nginx not on the node). I set `appVersion` to `1.25-alpine`, which was already cached, and added small resource requests because the minikube node is short on memory.
- **Broken jsonpath in my first Task 1 run.** My capture spec quoted `{"\n"}` wrongly and kubectl said `unterminated quoted string`. I switched to `-o jsonpath='{.type}'; echo` and re-ran the whole install-to-uninstall flow, so all Task 1 screenshots come from one run.
- **First uninstall check was too fast.** The pod was still `Terminating` when I listed the namespace, so I added `kubectl wait --for=delete pod --all` before the final `get`.
- **My own script deleted the repo file.** In the re-run I attached "reset the repo config" to the repo job by matching the word `repo` in the screenshot path, but every path contains `repos/devops-heros`, so the reset ran before every job. The repo screenshot (1.8) is still correct, but by clean-up time the repo file was gone and `helm repo remove` said `no repositories configured`. I recorded a separate `helm repo add` / `remove` run (screenshot `s15-23`).
- **NodePort from macOS.** With the Docker driver the minikube node IP is not reachable from the Mac, so I used `kubectl port-forward` (local ports 18501, 18510, 18520) to test the Services.
